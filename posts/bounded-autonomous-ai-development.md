最近在做一个 AI 招聘工作台时，我一直在想一件事：既然 AI 已经能读代码、写代码、运行命令和测试，为什么开发项目还要由我一步步推动？

常见的使用方式是，我告诉 Codex 做一个功能，它做完以后停下来；我检查，发现问题，再告诉它怎么改；改完以后，又由我决定下一步做什么。

AI 承担了不少编码工作，但整个项目的计划、调度、上下文传递和质量检查，依然落在我身上。项目越复杂，我越像一个不停给 AI 分配任务的项目经理。

我想要的不是这样的协作。我希望能把一个完整目标交给 AI，让它在既定边界内持续推进：规划、实现、测试、修复、集成。能独立处理的事情自己处理，真正需要我确认的问题先记录下来，最后集中交付。

这个目标听起来像“让 AI 一直跑”，但我逐渐意识到，**持续运行不等于自主交付**。

## 从一句需求到一个可执行的工程系统

假设我直接告诉 AI：“按照这份 PRD，把招聘系统开发完成，遇到问题自己处理。”

它确实可能连续写出大量代码。问题是，PRD 往往只说清楚要做什么，却没有充分说明模块边界、接口契约、异常情况和完成标准。

当一个模型同时承担需求解释、架构决策、编码和验收，容易出现一种情况：它按照自己的理解实现了一套系统，再用同一套理解证明自己做对了。

所以，我开始把开发依据分成四层：

| 层次 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| PRD | 我们为什么做、要做什么 | 用户场景、业务目标、功能边界 |
| Spec / Contract | 系统应该如何表现 | 数据模型、接口、状态、规则、异常 |
| Task | 当前这一轮做什么 | 目标、依赖、范围、交付物 |
| Test | 怎样证明它做对了 | 单元测试、集成测试、端到端验收 |

这些文件都留在 Git 仓库里，成为每次开发会话都能重新读取的事实来源。

我还会使用 ADR（架构决策记录）保存已经确定的技术选择，以及为什么这么选。比如我们已经决定由 LangGraph 负责招聘业务里的 AI 工作流，由 Temporal 负责长期业务任务，而浏览器自动化只是一种可替换的渠道接入方式。

新 Agent 可以提出更好的建议，但不能因为“这样写更方便”，就悄悄推翻已经确认的架构。

## 任务要拆，但不能只拆成待办清单

拆任务是必要的，却远远不够。

“实现人才库”对人而言已经是一个任务，对开发 Agent 来说仍然太模糊：有哪些字段？怎样去重？是否支持分页？候选人属于某一个项目，还是可以关联多个项目？简历从哪里来？保存和删除有什么规则？

我更希望把任务拆到**能够独立实现、独立验证，并能在其他任务中复用成果**的程度。

例如“实现候选人与招聘项目的匹配记录”这个任务，会明确它的输入、输出、依赖、不能修改的模块，以及验收条件。一个候选人可以匹配多个项目，每个项目的结论和依据独立存储。模型认为某人“符合要求”时，必须给出可追溯的证据，不能只有一个相似度分数。

同时，任务之间需要显式依赖。数据库结构还没确定，就不应该让多个 Agent 各自设计一套候选人字段；但前端视觉组件、技术文档和独立测试可以并行推进。

我用三个层次组织工作：**里程碑 → 功能 → 可验收任务**。这样 Agent 才知道先做什么，以及做到什么程度算完成。

## 一个任务，一个新的 Agent Session

长时间让 AI 使用同一个会话，看起来省去了重新解释背景的麻烦，实际上会把越来越多不相关的信息带进去。

一个会话刚讨论完数据库，又做了浏览器操作、UI 排版和部署排障。之前的失败尝试、临时决定和已经过时的讨论，都会占用上下文，甚至影响后续判断。

因此，我更倾向于每个任务启动一个新的开发 Session。

新 Session 不继承上一轮的完整聊天，而是重新读取：

- 项目目标与架构约束；
- 当前任务的 Spec、接口和依赖；
- 仓库里的真实代码与 Git 记录；
- 相关测试及上一次失败留下的交接信息。

这不意味着每轮都要把几十页 PRD 全部塞给模型。更好的方式是针对任务构建小型 Context Pack，只提供真正有关的资料，其他信息需要时再查。

**对开发来说，重要的不是记住聊过什么，而是能够找回已经确定的事实。**

## 让测试来推动下一步，而不是让 AI 自己宣布完成

如果目标是减少人工介入，就必须改变“完成”的定义。

代码写出来，不算完成。页面能打开，也不一定算完成。Agent 说“已经实现”，更不能当作验收证据。

我希望每个任务结束前都能运行相应检查：类型检查、Lint、单元测试、API 契约测试，以及必要的端到端测试。外部依赖尚未接通时，至少要有明确标记的离线测试；Mock 通过，不代表真实渠道已经跑通。

一个任务的基本循环应该是：

```text
读取任务与相关规格
    ↓
检查已有代码和依赖
    ↓
实现 → 运行测试 → 修复
    ↓
验收通过？
    ├─ 是 → 记录结果、提交、领取下一项
    └─ 否 → 继续修复，或记录阻塞
```

有些检查最好由独立的测试或审查机制完成，而不是让刚写完功能的 Agent 用自己的解释给自己打分。

测试还应该覆盖真实容易出错的地方。例如一个发送消息的操作在网络中断后重试，不能因此给同一位候选人发送两次。检查代码里有没有 `retry` 函数没有意义，真正需要模拟失败与恢复。

## 遇到阻塞，不等于整个项目停下

我最不希望看到的情况，是 AI 做到第三个任务，发现一个依赖无法安装，就把整套开发停在那里，等我回来告诉它下一步。

更合理的做法是把任务状态记录下来：`pending`、`running`、`completed`、`blocked`，同时保存失败原因、日志和已经验证的结果。

某个任务被阻塞，控制器就检查有没有其他不依赖它的任务可以做。比如暂时无法验证猎聘的浏览器接入，仍然可以实现招聘项目管理、人才库、匹配规则和 UI。

当然，自主不等于无限权限。我把操作分成三类：普通开发和测试可以自主进行；真实环境联调需要留出人工验收；发真实候选人消息、修改生产凭据、破坏性数据操作等高风险动作必须事先得到明确授权。

这也意味着，开发 Agent 的能力越强，越需要在工具权限、运行目录和外部副作用上设置边界，而不只是写一句“请谨慎操作”。

## 真正需要长期运行的，是控制器，不是一段超长对话

我的方案不是启动一个 Codex 会话，然后要求它连续工作几十个小时。

而是建立一个外部执行控制器：从任务清单里找到依赖已满足的工作，启动新的 Codex Session，等待结果，运行验收检查，更新任务状态，再决定是否执行下一项。

任务清单、Git 提交、测试报告和执行日志保存在项目目录中。即使控制器重启，也能从这些状态恢复，而不必依赖某一段聊天历史。

控制器还应该有明确的停止条件：任务全部完成、没有其他可执行任务、遇到必须人工授权的操作，或者出现无法安全恢复的故障。

这样，AI 的“自主”就变成了一个可观察、可暂停、可恢复的工程过程，而不只是一个充满雄心的 Prompt。

## 最终交付应该是一份报告，而不是一长串聊天

我希望未来检查项目时，不必先阅读 Agent 运行过的几十个 Session。

我更关心的是：哪些功能已经可以体验，哪些测试实际通过了，哪些地方只有模拟结果，哪些问题仍然阻塞，以及哪些决定必须由我来做。

所以，一个完整的交付至少应该包含：可运行的代码与演示地址、通过的测试、已知问题、待人工确认清单，以及相应的 Git 提交和部署说明。

我最近把这套思路用在 AI 招聘工作台的开发中：建立独立工作目录，用任务清单组织模块，给每项开发任务创建新的 Codex Session，并由控制器记录结果和继续分配工作。这个实践还在推进，沙箱权限、环境依赖和任务覆盖范围等问题，也让我更清楚地看到为什么执行控制和验收机制不能省略。

这并不保证 AI 会一次把所有功能都做好。但至少能够区分“它正在工作”“它认为完成了”和“系统已经通过验证”这三件不同的事。

## 我想减少的，是人作为调度器的工作

以前，人负责想目标，AI 负责执行，而人又不断负责解释背景、安排下一步、发现遗漏、检查结果。

如果我们能把目标、上下文、工作方法、权限边界和验收标准外置为一套稳定的工程系统，人就不必一直充当这个系统的手动调度器。

我仍然需要决定产品要解决什么问题、哪些取舍值得做，以及最后是否接受交付结果。但在这之间，大量明确、重复、可测试的工作，应该逐步交给 AI 自己推进。

**我追求的不是一个永远不停的 Agent，而是一个能够在约束内持续交付、出了问题也能解释清楚的开发系统。**
